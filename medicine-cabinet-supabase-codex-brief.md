# Промпт для Codex: подключение Supabase к PWA «Моя аптечка»

## Готовый промпт

Ты — senior full-stack engineer. Подключи существующее мобильное PWA «Моя аптечка» к Supabase и замени демонстрационное хранение в `localStorage` полноценной базой данных. Сохрани текущий визуальный дизайн и пользовательские сценарии. Работай автономно: сначала изучи репозиторий, затем реализуй, запусти проверки и исправь найденные проблемы.

Основные требования:

1. Supabase — основная база данных приложения.
2. Реализуй регистрацию, вход, выход и сохранение сессии.
3. Один пользователь может состоять в нескольких семейных аптечках.
4. Члены одной семьи видят общую аптечку; посторонние пользователи не имеют доступа.
5. Храни разные упаковки одного лекарства отдельно, потому что у них могут отличаться количество и срок годности.
6. Подключи Supabase Storage для фотографий упаковок.
7. Включи RLS для каждой таблицы в доступной приложению схеме и создай минимально необходимые политики.
8. Не помещай секретные ключи в клиентский код.
9. Перенеси существующие данные из `localStorage` один раз и без потери данных.
10. Подготовь Supabase Edge Function для обращения к OpenRouter: функция получает описание симптомов, безопасно загружает доступную пользователю аптечку и возвращает структурированный ответ ИИ.
11. Создай миграции, seed-данные, `.env.example` и понятную инструкцию запуска.
12. Проверь работу минимум с двумя разными пользователями и докажи, что RLS не позволяет видеть чужие данные.

Ниже приведено полное техническое задание. Если существующий стек отличается от примеров, адаптируй реализацию к текущему проекту, не переписывая рабочий интерфейс без необходимости.

## 1. Ожидаемый результат

После реализации пользователь должен иметь возможность:

- зарегистрироваться и войти;
- создать семейную аптечку;
- присоединиться к семейной аптечке по приглашению;
- добавлять, редактировать и удалять лекарства;
- хранить несколько упаковок одного препарата с разными сроками годности;
- загружать фотографию упаковки;
- видеть общий остаток и ближайший срок годности;
- фиксировать использование лекарства;
- добавлять закончившееся лекарство в список покупок;
- видеть изменения после перезагрузки и на другом устройстве;
- обратиться к ИИ, который учитывает только лекарства из доступной пользователю семейной аптечки.

Google Таблицы не являются рабочей базой. В будущем их можно использовать только для импорта или экспорта.

## 4. Схема данных

Используй UUID, `timestamptz`, внешние ключи, ограничения и индексы. Все изменяемые сущности должны иметь `created_at` и `updated_at`. Названия можно адаптировать под существующий стиль проекта, но смысл связей нужно сохранить.

### `profiles`

Публичный профиль, связанный с `auth.users`.

```text
id uuid primary key references auth.users(id) on delete cascade
display_name text not null
avatar_path text null
created_at timestamptz not null
updated_at timestamptz not null
```

Создавай профиль после регистрации безопасным серверным механизмом или trigger-функцией. Не используй пользовательские metadata для принятия решений о правах доступа.

### `households`

Семейные пространства с общей аптечкой.

```text
id uuid primary key
name text not null
owner_id uuid not null references auth.users(id)
created_at timestamptz not null
updated_at timestamptz not null
```

### `household_members`

```text
household_id uuid references households(id) on delete cascade
user_id uuid references auth.users(id) on delete cascade
role text check in ('owner', 'admin', 'member')
joined_at timestamptz not null
primary key (household_id, user_id)
```

В каждой аптечке должен оставаться минимум один владелец. Обычный `member` может работать с лекарствами, но не может удалять аптечку или управлять владельцами.

### `household_invites`

```text
id uuid primary key
household_id uuid references households(id) on delete cascade
token_hash text unique not null
created_by uuid references auth.users(id)
expires_at timestamptz not null
max_uses integer not null default 1
used_count integer not null default 0
revoked_at timestamptz null
created_at timestamptz not null
```

Не храни код приглашения в открытом виде. Создание и принятие приглашения выполняй через защищённую функцию/RPC или Edge Function. Проверяй срок, лимит использований и членство вызывающего пользователя.

### `medicines`

Карточка препарата внутри конкретной семейной аптечки.

```text
id uuid primary key
household_id uuid not null references households(id) on delete cascade
name text not null
inn text null
dosage text null
form text null
manufacturer text null
barcode text null
categories text[] not null default '{}'
indications text[] not null default '{}'
instructions text null
contraindications text null
photo_path text null
favorite boolean not null default false
created_by uuid not null references auth.users(id)
created_at timestamptz not null
updated_at timestamptz not null
```

Индексы:

- `(household_id, lower(name))` или эквивалентный индекс для поиска;
- `(household_id, barcode)`;
- GIN для `categories`, если фильтрация выполняется по массиву.

Не делай barcode глобально уникальным: разные карточки и упаковки могут использоваться в разных семьях.

### `inventory_batches`

Одна запись — одна конкретная упаковка или партия.

```text
id uuid primary key
household_id uuid not null references households(id) on delete cascade
medicine_id uuid not null references medicines(id) on delete cascade
initial_quantity numeric not null check (initial_quantity >= 0)
quantity numeric not null check (quantity >= 0)
unit text not null
expires_on date null
purchased_on date null
opened_on date null
storage_location text null
lot_number text null
notes text null
created_by uuid not null references auth.users(id)
created_at timestamptz not null
updated_at timestamptz not null
```

Обязательно обеспечь, чтобы `inventory_batches.household_id` совпадал с `medicines.household_id`. Сделай это составным внешним ключом, trigger-проверкой или другим надёжным ограничением базы.

Индексы:

- `(household_id, expires_on)`;
- `(household_id, medicine_id)`;
- частичный индекс для ненулевых остатков, если он оправдан запросами.

### `usage_logs`

```text
id uuid primary key
household_id uuid not null references households(id) on delete cascade
medicine_id uuid not null references medicines(id) on delete cascade
inventory_batch_id uuid null references inventory_batches(id) on delete set null
quantity numeric not null check (quantity > 0)
unit text not null
used_by uuid not null references auth.users(id)
used_at timestamptz not null
note text null
created_at timestamptz not null
```

Операцию «использовать лекарство» выполняй атомарно: создать журнал и уменьшить остаток в одной транзакции/RPC. Не допускай отрицательного остатка и повторного списания при повторной отправке запроса.

### `shopping_items`

```text
id uuid primary key
household_id uuid not null references households(id) on delete cascade
medicine_id uuid null references medicines(id) on delete set null
title text not null
desired_quantity numeric null
unit text null
status text check in ('needed', 'ordered', 'purchased', 'dismissed')
added_by uuid not null references auth.users(id)
created_at timestamptz not null
updated_at timestamptz not null
```

### `notification_preferences`

```text
user_id uuid references auth.users(id) on delete cascade
household_id uuid references households(id) on delete cascade
expiry_warning_days integer not null default 30
low_stock_enabled boolean not null default true
expiry_enabled boolean not null default true
primary key (user_id, household_id)
```

### История запросов ИИ

По умолчанию не сохраняй текст симптомов. Если UI позволяет сохранять историю, сделай это только после явного выбора пользователя. Для сохранения используй отдельные таблицы `ai_threads` и `ai_messages`, привязанные к `user_id` и `household_id`, с теми же RLS-ограничениями.

## 5. Представления и вычисляемые данные

Не дублируй агрегаты без необходимости. Для интерфейса нужны запросы или безопасные views/RPC, которые возвращают:

- общий остаток по препарату;
- ближайший срок годности;
- количество просроченных упаковок;
- количество упаковок, срок которых истекает в заданный период;
- наиболее часто используемые препараты;
- препараты с низким остатком.

Если создаёшь view в доступной приложению схеме, используй поведение `security_invoker`, чтобы RLS базовых таблиц продолжал применяться. Не создавай view, который незаметно обходит ограничения доступа.

## 6. Авторизация и семейный доступ

Для MVP реализуй:

- email + password или уже используемый в проекте способ Supabase Auth;
- экран регистрации;
- экран входа;
- восстановление доступа;
- выход;
- восстановление сессии после перезапуска PWA;
- создание первой аптечки после регистрации;
- переключение между аптечками, если пользователь состоит в нескольких;

Первый создатель household получает роль `owner`. Добавление первого участника и household должно выполняться атомарно.

## 7. RLS и разрешения

Включи RLS для каждой таблицы в `public` или иной exposed-схеме. Политики должны проверять не только роль `authenticated`, но и принадлежность `auth.uid()` к конкретной аптечке.

Матрица прав:

| Действие | Owner | Admin | Member |
| --- | ---: | ---: | ---: |
| Смотреть аптечку | Да | Да | Да |
| Добавлять и менять лекарства | Да | Да | Да |
| Фиксировать использование | Да | Да | Да |
| Управлять списком покупок | Да | Да | Да |
| Создавать приглашения | Да | Да | Нет |
| Удалять участников | Да | Ограниченно | Нет |
| Менять владельца/удалять аптечку | Да | Нет | Нет |

Избегай рекурсивных RLS-политик на `household_members`. Если потребуется helper-функция с `SECURITY DEFINER`, размести её в отдельной неэкспонируемой схеме, зафиксируй `search_path`, отзови `EXECUTE` у `PUBLIC`, предоставь только необходимой роли и обязательно проверяй `auth.uid()` внутри логики. Не используй `SECURITY DEFINER` просто для обхода ошибки доступа.

Для `UPDATE` создай корректные `USING` и `WITH CHECK`, чтобы пользователь не мог перепривязать запись к чужому `household_id` или `user_id`.

Проверь отдельно:

1. Пользователь A видит свою аптечку.
2. Пользователь B не видит аптечку A.
3. После вступления B в household A он видит общие записи.
4. B не может повысить себе роль.
5. Member не может удалить household или владельца.
6. Пользователь не может подменить `household_id` при insert/update.

## 8. Supabase Storage

Создай bucket `medicine-images`.

Путь объекта:

```text
{household_id}/{medicine_id}/{uuid}.webp
```

Требования:

- чтение и загрузка доступны только участникам household;
- удаление изображения разрешено owner/admin или автору карточки в рамках выбранной модели;
- перед загрузкой изображение уменьшается на клиенте до разумного размера и конвертируется в WebP/JPEG;
- ограничь размер и MIME-типы;
- при замене/удалении карточки не оставляй бесконечно копящиеся сиротские файлы;
- Storage policies должны проверять household по первому сегменту пути.

## 10. Перенос данных из `localStorage`

Создай одноразовую миграцию на клиенте:

1. После первого входа проверить наличие старых локальных данных.
2. Показать пользователю предложение перенести их в выбранную семейную аптечку.
3. Провалидировать структуру и даты.
4. Импортировать данные транзакционно или порциями с безопасным повтором.
5. Не удалять исходные данные до подтверждения успешного импорта.
6. После успеха сохранить версию миграции и резервную JSON-копию.
7. Не создавать дубликаты при повторном запуске.

Если фактическая структура `localStorage` отличается от ожидаемой, сначала создай явный mapper и тесты для него.

## 11. Интеграция OpenRouter через Edge Function

Создай функцию, например `analyze-symptoms`.

Поток:

1. Клиент передаёт `householdId`, текст симптомов и необязательные структурированные параметры.
2. Функция требует валидную пользовательскую сессию.
3. Функция проверяет членство пользователя через базу/RLS.
4. Функция сама загружает актуальные лекарства, остатки и сроки годности. Не доверяй присланному клиентом списку аптечки.
5. Просроченные препараты исключаются из рекомендаций.
6. Функция вызывает OpenRouter с ключом из server-side secret.
7. Ответ модели валидируется по строгой JSON-схеме.
8. Клиент получает структурированный результат и отображает его в существующем дизайне.

Пример результата:

```ts
type SymptomAnalysis = {
  summary: string;
  urgent: boolean;
  urgentMessage?: string;
  relevantMedicines: Array<{
    medicineId: string;
    reason: string;
    warnings: string[];
  }>;
  generalAdvice: string[];
  disclaimer: string;
};
```

Ограничения:

- модель не ставит диагноз;
- модель не назначает персональную дозировку;
- модель не рекомендует отсутствующие или просроченные препараты как имеющиеся дома;
- функция содержит базовый перечень красных флагов, обрабатываемых кодом до ответа модели;
- при опасных симптомах результат должен явно рекомендовать срочную медицинскую помощь;
- добавь rate limit и ограничение длины запроса;
- не логируй полный текст симптомов и секреты;
- при недоступности OpenRouter покажи корректное состояние ошибки;
- функция не должна использовать `service_role`, если задачу можно решить пользовательским JWT и RLS.

## 12. Сроки годности и количество

Статусы рассчитываются кодом или запросом из `expires_on`:

- `expired` — дата уже прошла;
- `expiring_soon` — срок наступит в пределах пользовательского периода предупреждения;
- `valid` — срок больше периода предупреждения;
- `unknown` — срок не указан.

Правила списания:

- по умолчанию предлагай упаковку с ближайшим непросроченным сроком;
- запрещай уход количества ниже нуля;
- при достижении нуля предлагай добавить препарат в список покупок;
- просроченную упаковку нельзя предлагать в сценарии симптомов;
- удаление журнала использования не должно незаметно менять остаток: либо реализуй корректный обратный RPC, либо запрети такое удаление через обычный UI.

## 13. Offline/PWA

Не обещай полноценное редактирование без сети на первом этапе.

- PWA shell и ранее загруженные экраны могут открываться офлайн;
- при отсутствии сети показывай последний локальный снимок аптечки только для чтения;
- операции изменения блокируй понятным сообщением или ставь в явно управляемую очередь;
- не создавай скрытую очередь списаний, которая может отправить одну операцию дважды;
- после восстановления сети обновляй данные с сервера.

## 17. Критерии готовности

Работа считается законченной, когда:

1. Интерфейс больше не зависит от моков или `localStorage` как основной базы.
2. Данные синхронизируются между двумя устройствами одного пользователя.
3. Семейная аптечка доступна всем добавленным участникам.
4. Посторонний пользователь не может прочитать или изменить чужие данные.
5. Несколько упаковок одного лекарства корректно отображаются и агрегируются.
6. Добавление, редактирование, удаление и списание лекарства реально работают.
7. Изображения загружаются с корректными Storage policies.
8. Старые локальные данные можно безопасно импортировать без дублей.
9. Edge Function вызывает OpenRouter без раскрытия ключа.
10. Все миграции воспроизводимы на новом Supabase-проекте.
11. Проект проходит typecheck, lint и production build.
12. README позволяет другому разработчику запустить проект без устных пояснений.
